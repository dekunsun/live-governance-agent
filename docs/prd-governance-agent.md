## 0. 一页摘要：要决定什么

直播治理平台已经有完整的策略 SOP 库、指标、变更日志和抽检样本，但策略 owner 每天仍要手动在后台操作，才能回答"处罚为什么涨了"和"这条策略还健不健康"。一次归因要跨多个页面、xxx 分钟，漏一步就错；巡检靠人记得去看；每次归因的推理过程留在聊天记录里，没有沉淀。

**提议**：在平台之上加一个**只读的会话式助手**。策略 owner 一句话提问，助手按 playbook 调用平台工具查证据，给出带证据编号的结论卡片；人确认、修改或推翻，每一次确认都变成训练样本。助手不直接改任何策略：策略修改只生成草稿走审批，资金类动作只标注"需要财务审批"。

**目标是三件事**：

1. 把一次归因从 xxx 分钟缩到 xx 分钟内，并且结论可追溯（每个结论都带证据编号，能回到平台核对）。
2. 把巡检和 policy 落地产品化：问题由系统定时发现并推送，policy 更新落成可回测的变更草稿。
3. 把每一次人工裁决变成训练自有模型的数据。

北极星指标是**每周经人确认的治理决策数**；护栏是采纳率 ≥ xx%、推翻率 ≤ xx%、幻觉 0、误处罚不劣于上线前（门槛由使用方按真实基线定，口径见第 5 节）。

**为什么值得做**：这类问题有确定性的标准做法和标准答案，所以能自动评测、能自动产生训练数据，这是它和通用对话助手的本质区别，也是"每用一次就更好一点"的前提。原型已经在合成世界上把整条链路跑通：规则引擎在标准答案题上全对、幻觉 0；一个 4B 开源模型经微调后，归因题 94%–96%、策略调整题 91%–98%（原型，合成数据）。

**请决定的事**：选下面哪个方案，以及谁来做试点运营团队。

| | 方案 A：最简 | 方案 B：推荐 | 方案 C：最完整 |
|---|---|---|---|
| 做什么 | 规则引擎按 playbook 自动归因，输出带证据编号的结论卡片；人确认 / 推翻；只读 | A + 开源小模型按规则引擎示范做微调，接自然语言提问；评估集与评分器；巡检推送；policy → 变更草稿（审批） | B + 用确认后的结论持续训练自有模型；多团队 playbook 平台化；内部模型路由…… |

## 1. 问题：谁在做什么，为什么慢、为什么错

主要用户是业务治理运营、风险策略、policy 团队和公会治理；地区运营通过收口方间接使用。

| 用户 | 每天要做的事 | 现在的路径（示意） | 痛点 |
|---|---|---|---|
| 业务治理运营 | 回答"某市场某场景昨天处罚为什么涨了" | 看板查处罚量 → 换页查同期流量 → 按策略下钻 → 翻变更日志 → 看分数分布 → 抽样看 case → 群里写结论。xxx 分钟 | 任何一步漏掉都得出错误结论（最常见：没排除流量上涨就归因为模型问题）；结论质量取决于个人经验 |
| 风险策略 | 判断"这条策略还健不健康"；模型升级后重校阈值 | 没有固定页面，靠记得去看精确率、申诉推翻率、命中集中度…… | 僵尸策略、重叠策略通常在出事后才被发现 |
| Policy 团队 | 把一条 policy 更新落成策略修改 | 读 policy → 找对应策略 → 手动试几个分数线 → 回测 → 写变更单。xxx 小时 | 试分数线靠手工，覆盖率、精确率、人审量三个约束容易顾此失彼 |
| 公会治理 | 解释"某公会健康分为什么掉了" | 按公会、主播下钻处罚和申诉 | 分不清真实违规和策略误杀造成的不合理扣分 |

归纳成四个问题：**归因慢且容易错**；**巡检没有产品化**；**知识没有沉淀**（推理过程留在聊天记录里，也没有数据训练模型）；**跨市场不一致**（同一类问题不同人判断，升级标准不统一）。

已有的办法为什么不够：看板 + 人工，数据都在但步骤靠人记；通用对话助手能聊，但不接平台工具、没有证据编号、没有确定性评分，无法自动评测，也无法把裁决变成训练数据；把规则写死成报表，覆盖不了"同一个症状、几种原因、几种动作"的判断分支。

## 2. 为什么现在能做

三个条件同时满足了：

1. **平台已经有数据和工具**：策略库、指标、变更日志、分数分布、抽检样本都在，缺的只是把"查、下钻、对照、下结论"这条路自动走一遍。
2. **这类问题有标准做法**：策略团队的 playbook（先排除流量 → 看增量集中在哪 → 查同期变更 → 看误判还是漏判）是固定的，可以写成文档，也可以直接当模型的 system prompt。
3. **有确定性的标准答案**：主因只有十来类，编号要么存在要么不存在，该不该升级有规则。这意味着评分可以是确定性的，于是能自动评测、能把评分当强化学习的奖励、能用规则引擎批量产生示范。原型用这个性质在合成世界上走完了"出题 → 评分 → 训练 → 评测"的全链路，结果在第 7 节。

这也是方案和通用型助手的分界线：通用助手靠满意度评价，这里靠标准答案；通用助手的错误是答得不好，这里的错误是改错一条影响整个市场的策略，所以只提方案、分级审批。

## 3. 方案：一个只读的助手，六步

1. **提问**：策略 owner 一句话提问（"某市场昨天误杀申诉涨了？"）。
2. **查证据**：助手按 playbook 调用平台的只读工具——查数、下钻、查变更、看漂移——每个结果都带证据编号；调用次数有上限（原型取 14）。
3. **结论卡片**：给出主因、证据编号、是否升级、建议动作；卡片里引用的每个策略 / 变更 / 公会编号，都必须是平台上真实存在、而且助手这次查到过的；凭空写出来的编号会被校验层拦下，结论退回重做；小市场、头部主播、资金侧的升级规则写死在护栏里。
4. **人工决策**：确认、修改后确认、或推翻并写原因；决策记录可追溯。
5. **沉淀样本**：只有经人确认的结论进入训练样本池，用于下一版模型。
6. **不直接改任何策略**：策略修改只生成变更草稿（回放结果 + 建议分数线）走审批流，通过后才生效；资金类动作只标注"需要财务审批"，不生成执行指令。

### 本期范围

| 优先级 | 事项 | 为什么是这一期 |
|---|---|---|
| P0 | 异常归因：一句话提问 → 带证据的结论卡片 → 人确认 / 修改 / 推翻 | 频次最高、步骤最标准、有确定性标准答案 |
| P0 | 评估集与评分器：标准答案题、确定性评分，每次发版跑回归 | 没有评测就没有发版依据，也没有后训练的奖励 |
| P1 | 策略健康巡检：定时扫描 → 推送给策略 owner | 复用归因的工具和评分器，增量小 |
| P1 | Policy-to-Strategy：policy 文本 → 可回测的策略修改草稿（仍需审批） | 价值高但风险高，所以放在"只出草稿"的边界内 |
| P2 | 用确认后的结论做后训练 | 依赖前面的样本积累；原型已验证技术路径 |

上线范围：一个策略团队，先 x 个大市场；小市场只读且样本不足时强制升级。

### 典型场景

- **异常归因（P0）**："某市场赌博场景这周误判率上升了。"先查流量排除流量驱动 → 按策略下钻 → 查同期变更 → 检查模型分数漂移 → "主因：模型升级后分数漂移，S-xxx 固定阈值失效；建议：评估阈值重校；不需要升级"。用户把建议分数线微调后确认。
- **没有异常 / 数据不足（P0）**：正常波动答"属正常波动，未发现异常"；小市场样本不足答"数据不足，建议扩大窗口或人工复核"。这两类在原型测试集里约占三分之一，是误报控制的关键。
- **公会健康分归因（P0）**：区分旗下主播的真实违规和策略误杀造成的不合理扣分；后者建议暂缓档位处置、重校后回补分数。
- **巡检发现并推送（P1）**：某条策略连续 xx 天命中为 0（僵尸）或两条策略命中高度重叠，推送给 owner，附证据与建议动作。
- **policy 更新落地（P1）**："某场景人审量不超过每天 xx 场，覆盖率不低于 xx%，精确率不低于 xx%"。找到对应的转人审策略，回测一组分数线，给出满足约束且留有余量的分数线，生成变更单草稿，标注是否涉及资金侧审批。

## 4. 边界：怎么保证它不出错

助手的错误后果是改错一条影响整个市场的策略，所以边界不靠模型自觉，靠代码。

| 情形 | 助手的行为 | 实现位置 |
|---|---|---|
| 写权限 | 没有写工具；唯一的"写"是生成草稿；草稿必须经审批流；资金类动作不生成草稿，只标注"需要财务审批" | 工具层 |
| 幻觉 | 引用的编号必须平台真实存在且本轮查到过；否则拒收并列出已见编号；评分器零容忍 | 校验层 |
| 何时澄清 | 缺市场或日期；问题同时指向多个策略而无法判断 | 范围解析（规则） |
| 何时调用工具 | 按 playbook 顺序：先流量，再下钻，再变更，再漂移 / 抽检；"处罚涨了"类问题没查流量不允许提交 | Harness 门控 |
| 何时说"不知道" | 小市场样本不足、数据窗口不全、数据矛盾 | 评分器把"数据不足"当正确答案 |
| 何时拒绝 | policy 条文解释、单个主播 / 公会的处置建议、治理分类法之外的问题 | 默认回答文案 |
| 何时转人工 | 资金侧、头部主播、处罚量周环比超过阈值、样本不足、同类结论连续被推翻、用户明确要求复核；升级时把完整轨迹和证据交给接手人 | 升级规则写死在护栏，不交给模型 |
| 可观测 | 每次运行留完整轨迹写入审计日志；playbook 和策略有版本号；总开关、按 playbook 开关、单次影响面上限 | 平台 |

**不做的事**：不做内容检测模型（只在策略和群体层面归因）；不直接执行策略修改和资金动作；不对单个主播、单个公会做处置建议；不替代 policy 条文解释；证据不足不给结论。责任归属：批准的人对决定负责，平台对助手质量负责。

## 5. 度量：怎么知道它好不好

| 类别 | 指标 | 口径 | 目标 / 基线 |
|---|---|---|---|
| 用户 | 经人确认的治理决策数（北极星） | 每周确认 + 修改后确认的卡片数 | 持续上升；若推翻率同步上升说明在走过场 |
| 用户 | 采纳率 / 推翻率 | 确认（含修改后确认）÷ 卡片数；推翻 ÷ 卡片数 | ≥ xx% / ≤ xx% |
| 业务 | 异常定位时长 | 从提问到 owner 确认结论，中位数 | xxx 分钟 → xx 分钟内（基线待使用方采集） |
| 业务 | 策略迭代周期 | 异常确认到修改上线的中位天数 | 缩短（基线待使用方采集） |
| 业务 | 误处罚水平 | 头部主播误处罚数、资金侧误杀金额、机构不合理扣分回补率 | 不劣于上线前 |
| 质量 | 标准答案集通过率 | 8 项标准全对的题数 ÷ 题数，每次发版回归 | ≥ xx%（原型在合成数据上 94%–96%） |
| 质量 | 幻觉率 | 引用了不存在或本轮未查到的编号 | 0（校验层硬拦） |
| 质量 | 升级正确率 | 该升级的升级、不该的不升级 | 按市场分层看，任一市场不明显落后于整体 |

两条口径上的提醒：原型的数字全部来自合成世界，衡量的是"与规则引擎一致"，不是现实准确率，上线前要用使用方标注的一批真实题做外部验证（模板见 [external-validation-template.md](external-validation-template.md)）；归因在单次运行间有约 ±8 题的波动（原型），门槛按多种子中位数定。真实基线的四个数（人工归因时长、人工结论被推翻率、策略迭代周期、误处罚水平）由使用方在上线前采集，口径见长版 PRD。

## 6. 上线：怎么一步步放开

| 阶段 | 用户 | 目标 | 退出条件 |
|---|---|---|---|
| 内测 | 产品 + x 位策略同学 | 标准答案集跑通，收集阻塞问题 | 标准答案集 ≥ xx%，幻觉 0 |
| 封闭 Alpha | 试点运营团队 x 人，归因只读，与人工并行 | 对比助手结论与人工结论 | 采纳率 ≥ xx%，推翻 ≤ xx%，没有未归类的失败 |
| 开放 Alpha | 同团队全体，开巡检推送 | 渗透率与巡检误报 | 任一市场准确率不明显落后于整体；巡检误报率可接受、重大问题不漏 |
| Beta | 第二个运营团队，开变更草稿（审批） | 复现 Alpha 结果 | 第二团队重复 Alpha 门槛；草稿返工率下降 |
| GA | 全部策略团队 | …… | …… |

灰度原则：先 x 个大市场、只读；按市场分层看准确率，任一市场掉队就停在该档；每升一档都要用并行对照的数据证明可靠。时间排期待定。

依赖：指标口径 owner（待对齐，平台只做承载）；指标、变更日志、抽检的只读接口；外部验证集与真实基线（使用方，上线前门槛）；审批流对接（Beta 前）；数据权限与保留期限走现有流程。

## 7. 为什么会越用越好：数据飞轮与原型证据

每一张卡片的确认、修改（带原值）、推翻（带原因）都进训练样本池；只收经人确认的，被推翻的题成为新测试题；随机抽一部分被采纳的结论做复核，作为无偏校准集。真实环境里，"规则引擎给的标准答案"换成"经人确认的结论"，评分器换成评估集，训练由算法团队执行。

原型在合成世界上验证了这条路技术上走得通，每一步只改一件事（原型：归因 194 道题、8 项标准全对才算过；策略调整 150 道题）：

| 步骤 | 改了什么 | 归因通过率 | 策略调整通过率 | 学到什么 |
|---|---|---|---|---|
| 规则引擎（参考） | — | 标准答案题全对 | — | 幻觉 0；作为教师和参考答案 |
| 4B 不训练 | — | 3.6% | 16% | 不是题难，是不会这套打法 |
| 一轮监督微调 | 规则引擎示范 374 条 | 79%–85%（3 种子） | 53%–63% | 示范里的"想法"必须由证据生成，不能是模板 |
| 补稀有类示范 | 示范 374 → 831 条 | 92%–94%（2 种子） | 69% | 召回下降类 0/11 → 11/11；先看错在哪类、补那类 |
| 换 8B，同样数据 | 只换模型 | 96% | 70% | 只比 4B 多对 4 题；数据质量比模型大小值钱 |
| 改策略调整示范的"想法" + 2 个 epoch | 示范写出约束、候选分数线和选择规则 | **94%–96%（2 种子）** | **91%–98%** | **当前可用版本**（4B） |
| 强化学习（GRPO）× 3 种子 | 在 SFT 之上 | +4 / +1 / 0 题（噪声内） | +3 / +7 / +17 题 | 收益远小于改示范；RL 放最后一步 |

三条对产品的含义：先修 Harness、再补示范、最后才是 RL，三者性价比差一个数量级；4B 够用，不必上大模型；数据侧的修法都很便宜（原型实测一次训练约 1 小时、不到 1 美元），真正的瓶颈是真实数据和真实标注。原型侧到此为止，下一步由使用方在试点运营团队里做只读并行对照。

## 8. 风险与开放问题

| 风险 | 影响 | 应对 |
|---|---|---|
| 用户不信任助手结论 | 采纳率低 | 并行对照、证据可见、随时切回平台 |
| 市场差异大、小市场数据少 | 归因错误集中在小市场 | 按市场评估，样本不足时强制升级 |
| 复杂场景助手不好用 | 结论不稳定 | 从标准化程度最高的流程切入，复杂场景保留人工 |
| 训练样本有偏（只有被质疑的结论被修改） | 后训练学到偏差 | 随机抽一部分被采纳的结论做复核，作为无偏校准集 |
| 合成数据上的数字不代表真实准确率 | 门槛定错 | 外部验证集作为上线前门槛；门槛按多种子中位数定 |
| 研发资源有限 | 与基建需求抢资源 | 用 ROI（人从操作转向判断的比例 × 可复用团队数）参与优先级排序 |

开放问题：平台的日常用户具体是哪几个团队、多少人，哪个团队的人工最重；策略评估与归因目前是否已平台化；助手参与的治理决策，人工审批边界由谁定；与策略产品、模型运营在训练和 playbook 编写上的分工；外部验证集由哪个团队标注、何时能有。

## 附录 B：交互流程

入口：平台常驻入口，打开后显示本周巡检发现和按当前页面推荐的冷启动问题；开场语说明"只读平台数据，结论都带证据编号，修改策略需要你确认"。调用过程以折叠行展示，可随时展开；卡片上的数值和主因可直接改，修改记录原值；会话长时间无交互自动结束并请求反馈。

一次会话的状态流转：

| 状态 | 进入条件 | 助手做什么 | 用户能做什么 | 下一状态 |
|---|---|---|---|---|
| S0 开场 | 打开入口 | 显示巡检发现和冷启动问题 | 选一个问题，或自己输入 | S1 |
| S1 范围解析 | 收到问题 | 解析市场 / 场景 / 日期；齐全则进入 S2 | — | S2 或 S1a |
| S1a 澄清 | 缺市场或日期 | 只问缺的字段，不查数 | 补充信息 | S1 |
| S2 查证据 | 范围齐全 | 按 playbook 调用只读工具（先流量 → 下钻 → 变更 → 漂移 / 抽检） | 展开任一步看证据；随时追问 | S3 |
| S3 提交门控 | 助手准备提交 | 检查：主因在枚举内、查过流量、编号都在本轮出现过；不通过则退回 S2 并提示 | — | S4 |
| S4 结论卡片 | 门控通过 | 展示主因、证据编号、是否升级、建议；命中升级规则时标"需要人工复核" | 确认 / 修改后确认 / 推翻（选原因）/ 追问 | S5、S2（追问）或 S6（升级） |
| S5 决策记录 | 用户点了确认或推翻 | 写入决策记录和样本池；若生成了草稿则提交审批 | 继续提问或结束 | S1 或 S7 |
| S6 升级 | 命中升级规则或用户要求复核 | 把完整轨迹、证据和结论交给接手人 | 等接手人处理 | S7 |
| S7 结束 | 用户结束或长时间无交互 | 请求反馈 | 反馈 | 回到 S0 |

![一次会话的状态流转](images/session-states.png)

多轮追问在同一会话内共享上下文；追问进入 Policy-to-Strategy 分支时，输出是变更草稿而不是归因卡片，按钮从"确认"变为"提交审批"。异常处理：工具调用失败重试一次，仍失败则报告缺什么，不编造；数据缺失或矛盾时停下并说明，给出可验证的部分。
