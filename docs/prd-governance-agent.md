## 1. Executive Summary（执行摘要）

直播治理平台已经有完整的策略 SOP 库、指标、变更日志和抽检样本，但策略 owner 每天仍要手动在后台操作，才能回答"处罚为什么涨了"和"这条策略还健不健康"等问题。本需求在现有平台之上加一个**只读的会话式助手**：策略 owner 一句话提问，助手按 playbook 调用平台工具查证据，给出带证据编号的结论卡片；人确认、修改或推翻，每一次确认都沉淀为训练样本。助手不直接改任何策略：策略修改只生成草稿走审批，资金类动作只标注"需要财务审批"。

目标是三件事：把一次归因从 30–60 分钟缩到 5 分钟内并且结论可追溯；把巡检和 policy 落地产品化；把每一次人工裁决变成训练自有模型的数据。北极星指标是**每周经人确认的治理决策数**，护栏是采纳率 ≥ 60%、推翻率 ≤ 10%、幻觉 0、误处罚不劣于上线前。

原型已在合成世界上跑通整条链路：规则引擎版标准答案题全对、幻觉 0；开源 4B 模型经监督微调后，194 道归因题 94%–96%、150 道策略调整题 91%–98%（两个种子）。全部数字只对合成数据成立，真实验证由使用方在上线前完成（见第 9、10 节）。

## 2. Background & Problem Statement（背景与问题）

### 现在的用户体验

| 用户要做的事 | 现在的路径（示意） |
|---|---|
| 回答"英国暴力血腥 10 月 14 日处罚为什么涨了" | 1. 打开指标看板查处罚量 → 2. 换页面查同期流量 → 3. 按策略下钻找增量来源 → 4. 翻变更日志看同期有没有模型升级 → 5. 打开分数分布页看漂移 → 6. 抽样看 case → 7. 在群里写结论。约 30–60 分钟，中间任何一步漏掉都会得出错误结论（最常见：没排除流量上涨就归因为模型问题） |
| 判断"这条策略还健不健康" | 没有固定页面；靠 owner 记得去看精确率、申诉推翻率、命中集中度。僵尸策略、重叠策略通常在出事后才被发现 |
| 把一条 policy 更新落成策略修改 | 读 policy 文本 → 找对应策略 → 手动试几个分数线 → 回测 → 写变更单。约半天 |

### 问题

1. **归因慢且容易错**：步骤多、口径陷阱多（流量、分母、小市场样本少），结论质量取决于个人经验。
2. **巡检没有产品化**：问题靠人记得去看，发现时往往已经造成误伤或漏放。
3. **知识没有沉淀**：每次归因的推理过程留在聊天记录里，新同学无法复用，也没有数据可以训练模型。
4. **跨市场不一致**：同一类问题在不同市场由不同人判断，升级标准不统一。

### 已有方案的不足

- **看板 + 人工**：数据都在，但"先排除流量、再下钻、再查变更"的步骤靠人记，漏一步就错。
- **通用对话助手**：能聊，但不接平台工具、没有证据编号、没有确定性评分，无法自动评测，也无法把裁决变成训练数据（对照见长版 PRD"与通用型助手的对照"）。
- **把规则写死成报表**：覆盖不了"同一个症状、五种原因、五种动作"的判断分支，也没有人机协作的回路。

## 3. Goals & Success Metrics（目标与成功指标）

| 类别 | 指标 | 口径 | 目标 / 基线 |
|---|---|---|---|
| 业务 | 异常定位时长 | 从提问到 owner 确认结论，中位数 | 30–60 分钟 → 5 分钟内（基线待使用方采集） |
| 业务 | 策略迭代周期 | 异常确认到修改上线的中位天数 | 缩短（基线待使用方采集） |
| 业务 | 误处罚水平 | 头部主播误处罚数、资金侧误杀金额、机构不合理扣分回补率 | 不劣于上线前 |
| 用户 | 经人确认的治理决策数（北极星） | 每周确认 + 修改后确认的卡片数 | 持续上升；若推翻率同步上升说明在走过场 |
| 用户 | 采纳率 / 推翻率 | 确认（含修改后确认）÷ 卡片数；推翻 ÷ 卡片数 | ≥ 60% / ≤ 10% |
| 质量 | 标准答案集通过率 | 8 项标准全对的题数 ÷ 题数，每次发版回归 | ≥ 80%（原型 4B 94%–96%，合成数据） |

| 质量 | 升级正确率 | 该升级的升级、不该的不升级 | 按市场分层看，任一市场不低于整体 10 个点 |

## 4. Target Users & Use Cases（目标用户与场景）

主要用户是 policy 团队、业务治理运营、公会治理和风险策略团队；地区运营通过收口方间接使用。

| 用户 | 今天的痛点 | 最需要的能力 | 本期优先级 |
|---|---|---|---|
| 业务治理运营 | 每天看大盘、下钻、拉 case，定位问题耗时；每周写归因和周报 | 异常归因、周会材料 | P0 |
| 风险策略 | 构建和迭代策略、定期人工评估线上效果、模型升级后重校阈值 | 策略健康巡检、分数漂移提醒、回测与变更草稿 | P1 |
| Policy 团队 | 政策更新后要确认线上策略是否对齐，靠人工抽 case | policy 更新后的策略对齐检查、case 证据包 | P1 |
| 公会治理 | 公会 / 主播维度的处罚和申诉波动，头部公会的问题要快速定位和解释 | 按公会下钻的归因、健康分归因 | P0（归因）；处置建议不做 |

### 主要场景

**场景 1：异常归因（P0）。** 用户："印尼赌博场景这周误判率上升了。"助手先查流量排除流量驱动 → 按策略下钻 → 查同期变更 → 检查模型分数漂移 → 给出"主因：模型升级后分数漂移，S-116 固定阈值失效；建议：策略 owner 评估阈值重校；不需要升级"。用户把建议分数线从 0.92 改成 0.90 后确认。

**场景 2：没有异常 / 数据不足（P0）。** 用户问一个其实正常的波动，助手答"属正常波动，未发现异常"；小市场样本不足时答"数据不足，建议扩大窗口或人工复核"。这两类占测试集约三分之一，是误报控制的关键。

**场景 3：巡检发现并推送（P1）。** 每日巡检发现某条策略 14 天命中为 0（僵尸）或两条策略命中高度重叠，推送给 owner，附证据与建议动作。

**场景 4：policy 更新落地（P1）。** Policy 更新"赌博人审量不超过每天 28 场，覆盖率不低于 78%，精确率不低于 92%"。助手找到对应的转人审策略，回测一组分数线，给出满足三个约束且留有余量的分数线，生成变更单草稿，标注是否涉及资金侧审批。

**场景 5：公会健康分归因（P0）。** "某公会健康分为什么掉了"：区分旗下主播的真实违规和策略误杀造成的不合理扣分；后者建议暂缓档位处置、重校后回补分数。

## 5. Scope & Non-Goals（范围与非目标）

### 三个方案，供决策

| | 方案 A：最简 | 方案 B：推荐 | 方案 C：最完整 |
|---|---|---|---|
| 做什么 | 规则引擎按 playbook 自动归因，输出带证据编号的结论卡片；人确认 / 推翻；只读 | A + 开源小模型（4B）按规则引擎示范做监督微调，接自然语言提问；评估集与评分器；巡检推送；policy → 变更草稿（审批） | B + 用确认后的结论持续训练自有模型（RL 放最后）；多团队 playbook 平台化；内部模型路由；配置化巡检 |
| 不做什么 | 不接模型，问法固定（从冷启动问题里选）；不做巡检和草稿 | 不做自有模型的持续训练；不做多团队 | — |
| 能拿到什么 | 归因时间从 30–60 分钟降到分钟级，结论可追溯；原型已证明规则引擎在标准答案题上全对、幻觉 0 | 自然语言提问、新问法可泛化；合成测试集上归因 94%–96%、策略调整 91%–98%；每次确认都变成训练样本 | 能力随使用持续提升；策略团队自己写 playbook |
| 依赖 | 平台只读接口 | A 的依赖 + 一张 GPU（一次训练约 1 小时）+ 试点运营团队做并行对照 + 外部验证集标注 | B 的依赖 + 算法团队承接训练 + 审批流对接 |
| 周期（估） | 2–4 周接入试点 | 一个季度到封闭 Alpha | 两个季度以上 |
| 主要风险 | 问法和场景一多就要不停写规则 | 分数只对合成数据成立，真实准确率要靠外部验证；用户信任 | 口径对齐、跨团队分工、训练样本偏差 |
| 适合 | 想先验证"有没有人用"，预算和人力最少 | 想把这件事做成产品并沉淀数据 | 已经决定把治理平台 Agent 化作为年度目标 |

本文按方案 B 写；A 是 B 的第一步（规则引擎已在原型里跑通），C 是 B 的延伸。

### 本期做什么

| 优先级 | 事项 | 为什么是这一期 |
|---|---|---|
| P0 | 异常归因：一句话提问 → 带证据的结论卡片 → 人确认 / 修改 / 推翻 | 频次最高、步骤最标准、有确定性标准答案，最适合先做 |
| P0 | 评估集与评分器：标准答案题、8 项确定性评分，每次发版跑回归 | 没有评测就没有发版依据，也没有后训练的奖励 |
| P1 | 策略健康巡检：定时扫描 → 推送给策略 owner | 复用归因的工具和评分器，增量小 |
| P1 | Policy-to-Strategy：policy 文本 → 可回测的策略修改草稿（仍需审批） | 价值高但风险高，所以放在"只出草稿"的边界内 |
| P2 | 用确认后的结论做后训练（SFT → RL），把能力沉淀到自有模型 | 依赖前面的样本积累；原型已验证技术路径可行 |

上线范围：一个策略团队，6 个市场中的 2 个大市场先行；小市场只读且样本不足时强制升级。

### 不做什么（以及原因）

- **不做内容检测模型**：助手只在策略和群体层面归因，不判断单场直播是否违规。
- **不直接执行策略修改和资金动作**：只生成草稿走审批；资金类动作连草稿都不生成，只标注"需要财务审批"。错误后果是整个市场的处置，必须留在人手里。
- **不对单个主播、单个公会做处置建议**：避免把归因工具变成处罚工具。
- **不替代 policy 条文解释**：超出治理分类法的问题转到对应文档或人。
- **证据不足不给结论**：小市场、样本少、窗口不全时答"数据不足"或"需要澄清"，不猜。

## 6. User Journey & Interaction Workflow（用户旅程与交互流程）

### 六步流程

1. **提问**：策略 owner 一句话提问（"美国昨天误杀申诉涨了？"）。
2. **查证据**：助手按 playbook 调用平台的只读工具——查数、下钻、查变更、看漂移——每个结果都带证据编号；最多 14 次调用。
3. **结论卡片**：给出主因、证据编号、是否升级、建议动作；卡片里引用的每个策略 / 变更 / 公会编号，都必须是平台上真实存在、而且助手这次查到过的；凭空写出来的编号会被校验层拦下，结论退回重做；小市场、头部主播、资金侧的升级规则写死在护栏里。
4. **人工决策**：确认、修改后确认、或推翻并写原因；决策记录可追溯。
5. **沉淀样本**：只有经人确认的结论进入训练样本池，用于下一版模型。
6. **不直接改任何策略**：策略修改只生成变更草稿（回放结果 + 建议分数线）走审批流，通过后才生效；资金类动作只标注"需要财务审批"，不生成执行指令。

### 交互流程（一次会话的状态流转）

| 状态 | 进入条件 | 助手做什么 | 用户能做什么 | 下一状态 |
|---|---|---|---|---|
| S0 开场 | 打开入口 | 显示本周巡检发现（≤ 3 条）和当前页面的 3 个冷启动问题 | 选一个问题，或自己输入 | S1 |
| S1 范围解析 | 收到问题 | 解析市场 / 场景 / 日期；齐全则进入 S2 | — | S2 或 S1a |
| S1a 澄清 | 缺市场或日期 | 只问缺的字段，不查数 | 补充信息 | S1 |
| S2 查证据 | 范围齐全 | 按 playbook 调用只读工具（先流量 → 下钻 → 变更 → 漂移 / 抽检），每步以折叠行展示；≤ 14 次 | 展开任一步看证据；随时追问 | S3，或预算用尽时 S3（"数据不足"） |
| S3 提交门控 | 助手准备提交 | 检查：主因在枚举内、查过流量、编号都在本轮出现过；不通过则退回 S2 并提示 | — | S4 |
| S4 结论卡片 | 门控通过 | 展示主因、证据编号、是否升级、建议；命中升级规则时顶部标"需要人工复核" | 确认 / 修改后确认 / 推翻（选原因）/ 追问 | S5、S2（追问）或 S6（升级） |
| S5 决策记录 | 用户点了确认或推翻 | 写入决策记录和样本池；若生成了草稿则提交审批 | 继续提问或结束 | S1 或 S7 |
| S6 升级 | 命中升级规则或用户要求复核 | 把完整轨迹、证据和结论交给接手人 | 等接手人处理 | S7 |
| S7 结束 | 用户结束或 2 小时无交互 | 请求反馈（有用 / 没用 + 原因） | 反馈 | 回到 S0 |

![一次会话的状态流转](images/session-states.png)

多轮追问在同一会话内共享上下文：第二轮"分数线调到多少合适"直接沿用第一轮解析出的市场、策略和证据，不重新解析；追问进入 Policy-to-Strategy 分支时，输出是变更草稿而不是归因卡片，按钮从"确认"变为"提交审批"。

### 异常处理

- **范围解析不出**（缺市场或日期）：先澄清，不猜。
- **工具调用失败**：重试一次，仍失败则报告缺什么，不编造。
- **数据缺失或矛盾**：停下并说明，给出可验证的部分。
- **调用预算用完**：剩 2 次时提示尽快提交；没把握就选"数据不足"或"需要澄清"。
- **用户否定结论**：记录为推翻样本，进入每周复盘；同一类结论连续两次被推翻则触发升级。

## 7. Functional Requirements（功能需求）

| # | 功能 | 触发条件 | 输入 | 系统行为 | 输出 | 验收标准 |
|---|---|---|---|---|---|---|
| F1 | 异常归因 | 用户提出"处罚 / 命中 / 误判变化"类问题 | 自然语言问题；解析出的市场、场景、日期 | 按 playbook 调用只读工具（≤ 14 次）；先查流量；编号校验；命中升级规则时标记 | 结论卡片：主因（枚举）、策略 / 变更 / 公会编号、是否升级、一句话结论、建议动作 | 标准答案集 ≥ 80%；幻觉 0；单次 < 3 分钟 |
| F2 | 范围澄清 | 问题缺市场或日期 | 同上 | 不查数，先反问缺失字段 | 澄清问题 | "需要澄清"类题 100% 先澄清 |
| F3 | 没有异常 / 数据不足判断 | 波动在正常范围，或样本低于阈值 | 同上 | 对照前 7 天中位数；小市场按样本阈值判断 | "属正常波动"或"数据不足，建议扩大窗口或人工复核" | 这两类在测试集中约 1/3，误报率可接受 |
| F4 | 调用过程可见 | 每次工具调用 | 工具名、参数 | 折叠行展示调用与返回（带证据编号） | 可展开的轨迹 | 每张卡片都能回溯到证据 |
| F5 | 人工修改 | 用户改卡片字段 | 新值 | 记录原值与新值，标记"修改后确认" | 修改类样本 | 修改被完整记录 |
| F6 | 确认 / 推翻 | 用户点按钮 | 推翻原因（主因错 / 证据不足 / 口径错 / 其他） | 写入决策记录与样本池 | 决策记录 | 推翻必须带原因 |
| F7 | 升级 | 命中资金侧、头部主播、处罚量周环比 ×2、小市场样本不足 | 卡片与轨迹 | 卡片顶部标"需要人工复核"，把完整轨迹和证据交给接手人 | 升级记录 | 升级正确率按市场看 |
| F8 | 策略健康巡检（P1） | 定时 | 全部线上策略 | 扫描效果下降、长期不命中、重叠、分数漂移；已暂停策略与预期内变化标为提示 | 待处理清单推送 | 误报率可接受、重大问题不漏 |
| F9 | 变更草稿（P1） | policy 更新或用户要求调分数线 | policy 文本或目标 | 找目标策略；回放一组分数线；取满足约束且留余量的线 | 变更单草稿：目标策略、分数线、动作、是否需财务审批、回测结果；只能"提交审批" | 草稿返工率下降 |
| F10 | 反馈 | 每张卡片 | 有用 / 没用（原因） | 记录 | 质量样本 | "没用"必须选原因 |

主因枚举：模型漂移、召回下降（规避）、流量驱动、policy / 策略变更、新策略上线、公会集中违规、公会真实违规、公会不合理扣分、没有异常、数据不足、需要澄清。

## 8. AI Behavior & Guardrails（AI 行为与护栏）

| 情形 | 助手的行为 | 实现位置 |
|---|---|---|
| 何时回答 | 问题在治理分类法内、市场 / 场景 / 日期齐全、证据足够时给结论卡片 | playbook + 提交门控 |
| 何时澄清 | 缺市场或日期；问题同时指向多个策略而无法判断 | 范围解析（规则） |
| 何时调用工具 | 按 playbook 顺序：先流量，再下钻，再变更，再漂移 / 抽检；"处罚涨了"类问题没查流量不允许提交 | Harness 门控 |
| 何时说"不知道" | 小市场样本不足、数据窗口不全、数据矛盾 | 评分器把"数据不足"当正确答案 |
| 何时拒绝 | policy 条文解释、单个主播 / 公会的处置建议、治理分类法之外的问题 | 默认回答文案 |
| 何时转人工 | 资金侧、头部主播、处罚量周环比 ×2、样本不足、同类结论连续两次被推翻、用户明确要求复核 | 升级规则写死在护栏，不交给模型 |
| 幻觉控制 | 引用的编号必须平台真实存在且本轮查到过；否则拒收并列出已见编号；评分器零容忍 | 校验层 |
| 写权限 | 没有写工具；唯一的"写"是生成草稿；草稿必须经审批流；资金类动作不生成草稿 | 工具层 |
| 调用预算 | 单次归因 ≤ 14 次；剩 2 次提醒 | Harness |
| 可观测 | 每次运行留完整轨迹写入审计日志；playbook 和策略有版本号；总开关、按 playbook 开关、单次影响面上限 | 平台 |

责任归属：批准的人对决定负责，平台对助手质量负责。

## 10. Risks, Open Questions & Appendix（风险、开放问题与附录）

### 风险

最大的风险不是技术，而是口径对齐和用户信任。

| 风险 | 影响 | 应对 |
|---|---|---|
| 用户不信任助手结论 | 采纳率低 | 并行对照、证据可见、随时切回平台 |
| 市场差异大、小市场数据少 | 归因错误集中在小市场 | 按市场评估，样本不足时强制升级 |
| 复杂场景助手不好用 | 结论不稳定 | 从标准化程度最高的流程切入，复杂场景保留人工 |
| 训练样本有偏（只有被质疑的结论被修改） | 后训练学到偏差 | 随机抽一部分被采纳的结论做复核，作为无偏校准集 |
| 合成数据上的数字不代表真实准确率 | 门槛定错 | 外部验证集作为上线前门槛；归因单次运行波动 ±8 题，门槛按多种子中位数定 |
| 研发资源有限 | 与基建需求抢资源 | 用 ROI（人从操作转向判断的比例 × 可复用团队数）参与优先级排序 |
