### 1.1 全量扫描：没有埋点的地方会不会乱报？

标准答案集只覆盖我们知道答案的地方。为了量化误报，`run_eval.py --sweep` 对 **6 市场 × 8 场景 × 近 7 天 × 涨/跌两种问法 = 672 次提问**逐一归因：

| 结果 | 次数 | 说明 |
|---|---|---|
| 无埋点、正确判为正常/流量驱动 | 384 | |
| 无埋点、小市场正确升级 | 218 | VN/KE 全部按规则拒绝下结论 |
| 无埋点、报了「无法解释」 | **10（5 个格子 × 2 问法）→ 1.6%** | 随机噪声超过 2.5σ（如 US 色情 10-15 处罚 25→42），引擎诚实地说「无法解释，需人工」并升级，没有编造原因 |
| 有埋点、找对主因 | 26 + 26（时间窗外仍可见） | |
| 有埋点、小市场升级 | 6 | 正确行为 |
| 有埋点、漏判为正常 | **2** | BR 赌博 10-10（下降刚开始，21 vs 28 还不显著）；ID 未成年 10-15（单日 43 vs 42；7 天回退窗口 ×1.29，差一点到 1.3 的门槛） |

误报率 1.6%、埋点检出率 76.5%（含 7 天内的全部日期；若只算变更当天起 3 天内则为 100%）。

## 2. 失败分析（开发期发现并修复 / 仍存在）

按 PRD 的五个桶归类。「状态」里标明是否已修。

| # | 现象 | 根因 | 桶 | 状态 / 修法 |
|---|---|---|---|---|
| F1 | 「美国昨天误杀申诉涨了」（没说场景）判为正常：市场整体 50 vs 44 在噪声内，诈骗场景的 3→13 被稀释 | playbook 只在市场层做异常判定 | playbook 不全 | 已修：整体平稳时自动按场景下钻，报「整体正常但 X 场景异常」 |
| F2 | 校验层把 `model_drift_threshold`、`model_update` 当成不存在的模型名 | 正则 `model_[a-z_]+` 过宽 | 工具/校验层 | 已修：模型名只匹配已知场景 + 词表排除；用户自己输入的 id 不算幻觉 |
| F3 | GB 骚扰人审量涨：找不到贡献策略 → 判为「无法解释」 | 按策略的指标表没有 manual_reviews 字段 | 工具缺失 | 已修：补字段。这正是 PRD 说的「别人要一个字段就开一个接口」的反例——补在公共指标服务里 |
| F4 | 「巴西赌博命中最近下降了」判为正常 | 单日 vs 前 7 天中位数：下降从 10-08 开始，到 10-15 基线已经被拉低 | SOP 本身 | 已修：「最近」用 7 天合计 vs 前 14 天日均；单日正常时自动回退到 7 天窗口 |
| F5 | 「误杀率涨了」被当成计数处理，报样本不足 | 比率指标没有单独路径 | playbook 不全 | 已修：比率先做比例检验，再按分子下钻；结论里先说明口径 |
| F6 | 巡检把 US 色情、US/BR 暴力报为「召回下降」 | recall_est 用分层抽样估计，未举报层 20 条/天权重 50，一个样本就能把估计拉低 0.3 | 数据口径 | 已修：随机层加到 50/天；召回告警要求命中也同步下降 ≥ 30%（多信号）。**真实平台上 recall 估计同样噪声大，这是上线前必须和 DS 对齐的口径** |
| F7 | 大市场里小计数（3→8）被报为「样本不足并升级」 | 样本量规则只看计数不看市场规模 | playbook 不全 | 已修：大市场小计数 → 做 Poisson 检验，不显著则「正常波动」 |
| F8 | 巡检对 S-110/S-114 报漂移，但它们的精确率没变差 | 只看分布漂移不看结果 | playbook 不全 | 已修：漂移 + 精确率下降 ≥ 0.1 才算告警，否则 low 级观察 |
| F9 | 用户说「下降了」而数据实际上升时，引擎照着上升分析却不提醒 | 没核对用户前提 | playbook 不全 | 已修：结论前加「注意：你说的是下降，数据显示实际上升」 |
| F10 | 随机噪声导致的「无法解释」告警（扫描中 1.6%） | 基线用前 7 天中位数，没有同星期对照 | SOP 本身 | **未修**。改进方向：同星期基线、或先问「这周末有活动吗」。当前行为（说不知道并升级）是可接受的保守失败 |
| F11 | ID 未成年 10-15 漏判 | 7 天窗口比率 1.29 < 1.3 | 阈值 | **未修**，不为单个 case 调门槛；真实上线后用误报/漏报曲线定 |
| F12 | 「巴西赌博 10-15 处罚下降了」判为正常 | 处罚计数本身就小（7~15/天），单日不显著 | 数据口径 | **未修**，属实；正确做法是看命中或召回，卡片里应主动建议换指标（待做） |

修复后全部跑回归（30 条标准答案 + 672 次扫描），确认没有改坏其他场景。

## 3. 读数时要注意的局限

1. **规则引擎是照着埋入问题写的。** 数据、标准答案、引擎出自同一人之手，100% 不代表泛化能力；它证明的是评估框架能跑、门槛能卡、失败能归类。有信息量的数字是扫描误报率（1.6%）和开发期的 12 个失败模式。
2. **一致性对确定性引擎没有意义。** 这项是给 LLM 引擎准备的。
3. **recall_est 的噪声**（F6）在真实平台只会更大。上线前要和 DS 对齐分层抽样方案和置信区间展示方式。
4. **升级规则是代码写死的护栏**，不依赖模型记得：样本不足、头部主播、数据缺失、口径冲突。LLM 引擎的卡片同样要过这一层。

## 4. LLM 引擎：已做什么、还差什么

- 已做：Claude（`claude-opus-5-5`）tool-use 回路（`agent/run.py: LLMEngine`），playbook 为 system prompt，9 个平台工具 + strict 的 `submit_card`；校验层发现引用不存在的 id 会打回一次要求重提；护栏统一处理升级；trace 记录每次模型调用的 token 和成本（按 $4 / $20 每百万 token 估算）。
- 已测：`tests/test_llm_mock.py` 用脚本化的假 client 走完「工具调用 → 幻觉 id 被拦 → 重提 → 通过护栏」全流程。
- 未测：真实模型的准确率、幻觉率、一致性（5 次）、延迟和成本。有 `ANTHROPIC_API_KEY` 的环境运行：

```bash
python eval/run_eval.py --engine llm --repeats 5
python eval/run_eval.py --engine llm --sweep      # 672 次调用，先估算成本
```

- 预期的 LLM 特有失败模式（评估时重点看）：
  - 跳过「先查流量」直接下钻 → 掉进流量陷阱；
  - 把 ambiguous_metric 错误当成失败而不是去选一个口径；
  - 引用 ref_id 时张冠李戴（Q-0003 的数字配 Q-0005 的描述），校验层查不出来，需要抽样人审；
  - 小市场仍给 high 置信度（护栏会压到 low，但结论文字可能仍很笃定）。
